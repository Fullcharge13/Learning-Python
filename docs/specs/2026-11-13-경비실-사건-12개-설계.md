# 「경비실」 사건 12개 + 장별 파일 설계 (v0.16.0)

- 작성일: 2026-11-13 · 상태: **사용자 검토 대기**
- 브랜치: `feature/guard-room` (v0.15.0 경비실 첫 판 위에 이어서)
- 바탕: `docs/specs/2026-11-12-경비실-설계.md`(v0.15.0, 사건 6개), 레슨 장 파일 나누기(`build.py` 머리 설명, `src/lessondata.js`)

## 1. 의도와 왜

- 사용자가 정한 방향: **배우는 장마다 그 장의 파이썬 문법을 쓰는 경비실 사건이 기본 3~5개** 있고, 나중에 기본·심화로 나눈다.
- 이번 판(사용자 선택 A): **3~6장을 장마다 3개로** 맞춘다 — 지금 6개(3장 2·4장 1·5장 2·6장 1) + 새로 6개 = 12개.
- 사건이 계속 늘어날 것이므로, 사건 본문을 앱 첫 파일에서 떼어 **장별 파일**로 둔다(사용자 선택 A). 첫 파일은 첫 화면이 뜨기 전에 받아야 하는 유일한 파일이라, 사건 수와 상관없이 가볍게 유지한다.

## 2. 목표 · 하지 않을 것 · 실패로 볼 것

**목표**
- 3·4·5·6장마다 사건 3개, 모두 그 장까지 배운 문법만으로 풀린다.
- 사건 본문은 `guard/chN-<지문>.json`으로 빠지고, 첫 파일에는 작은 색인만 남는다.
- 첫 파일(`dist/index.html`)이 사건 12개를 넣고도 **v0.15.0의 844.6KB보다 작다**.
- 오프라인에서도 경비실이 열린다(장별 파일을 서비스 작업자가 미리 받음).

**하지 않을 것 (이번 판)**
- 장마다 4~5개로 늘리기, 기본·심화 나누기, 7장 이후 사건 — 다음 판.
- 첫 화면 속도 최적화 프로젝트 — 사용자 요청으로 「나중에 할 일」, 이번 판 뒤 따로 설계.
- 크로우 새 포즈.

**실패로 볼 것 (테스트가 통과해도)**
- 이미 푼 사건 기록(G1~G6)이 사라지거나 XP를 다시 받는다.
- 경비실을 열 때 장 파일을 못 받으면 빈 화면이나 멈춘 화면이 된다.
- 오답 보기로도 풀리는 사건이 있다(효과 없는 보기).
- 첫 파일이 v0.15.0보다 커진다.

## 3. 제약 (v0.15.0 그대로)

- 공격은 가상 사건, 학습자 코드는 방어 쪽만. 인물·주소는 가상(`.example` 도메인만).
- 코드 속 이름은 한·영 공통 영어(`attempt`, `password`, `block()`, `allow()`, `has_try()`, `next_try()`, `check`). 시도 값만 언어별로 다를 수 있다(`value_en`).
- 영어 글은 `i18n/en/data.json`의 `guard.<id>.*` 열쇠(영어 팩은 이미 첫 파일 밖의 `lang/en-<지문>.json`).
- 사건 첫 해결에만 XP 5, 바이트는 직접 주지 않는다(판정 G-C2).
- 첫 파일 상한 850KB(판정 G-C6)는 그대로 두되, 이번 판 목표는 위 「목표」의 844.6KB 미만.
- `saveVer` 2 그대로. `save.garden` 손대지 않음.

## 4. 만드는 방법 (사용자가 A를 고름)

| | 방법 | 장단점 | 결정 |
|---|---|---|---|
| **A** | 사건 본문을 장별 JSON 파일로, 첫 파일엔 색인만 (레슨과 같은 방식) | 첫 파일이 약 10KB 가벼워지고, 몇 개로 늘어도 첫 화면 속도가 같다. 경비실을 열 때 장 파일을 받는 짧은 단계가 생긴다 | **채택** |
| B | 레슨 파일 안에 경비실 칸을 넣기 | 새 불러오기 코드가 적지만 레슨과 경비실이 한 파일에 묶여 서로의 시험·갱신이 얽힌다 | 버림 |
| C | 첫 파일에 두고 한도를 870KB로 | 가장 빠르지만 판마다 한도를 다시 올려야 하고 첫 로딩이 계속 무거워진다 | 버림 |

## 5. 정해진 것

### 5-1. 데이터 원본과 빌드

- 원본은 지금처럼 `data/guard.js`의 `INCIDENTS` **한 곳**(사건 12개, 장 순서). 시험(`tests/guard_incidents.py`, 단위 시험)은 계속 이 원본을 읽는다.
- 빌드(`build.py`)가 레슨처럼 나눈다:
  - `guard/chN-<지문>.json`: 그 장 사건들의 전체 본문(한국어 글, `start`, `blanks`, `solution`은 넣지 않음, `tries`, `crow`, `password`). 지문 = 파일 내용 sha256 앞 8자(레슨과 같음).
  - `window.RIA_GUARD_INDEX`(첫 파일): 사건마다 `{ id, need, mode, tag, title, blanks: [보기 수, …] }`. `title`은 한국어(영어는 영어 팩).
  - `window.RIA_GUARD_FILES`(첫 파일): `{ 장 번호: "guard/chN-<지문>.json" }`.
  - 서비스 작업자 미리 받기 목록에 장별 파일을 넣는다(레슨 장 파일과 같은 줄).
- `solution`은 배포 파일에 넣지 않는다(시험 전용, 정답 노출 방지·크기 절약).
- 개발 모드(`tools/dev.py`)는 지금처럼 `data/guard.js`를 직접 읽는다(레슨의 `lessondev.js`와 같은 갈래).

### 5-2. 앱

- 새 모듈 `src/guard/data.js`: `guardIndex() -> 색인 목록`, `loadIncidents(chapter) -> Promise<사건[]>`(한 번 받은 장은 기억). 배포판은 `RIA_GUARD_*`, 개발판은 `data/guard.js`.
- 첫 파일에 남는 쪽(목록·등급·배지·새 소식 점·저장 다듬기)은 **색인만** 쓴다. `cleanGuard`의 빈칸 검사는 색인의 `blanks`(보기 수)로 한다.
- 사건 화면을 열 때 그 장 파일을 받는다. 받는 동안 「사건을 불러오는 중」, 실패하면 「사건을 불러오지 못했어요」 + 「다시 시도」 단추. 실행·재생은 본문이 있을 때만.
- `guardInput`·`guardConsistent`는 본문(시도 목록)이 필요하므로 받은 사건으로만 부른다.

### 5-3. 번호·등급·배지·XP

- 기존 G1~G6 그대로, 새 사건 **G7~G12**. 목록은 장 순서(3장 G1·G2·G7, 4장 G3·G8·G9, 5장 G4·G5·G10, 6장 G6·G11·G12).
- 보안 등급 기준(해결 수): **0 견습 문지기 · 4 문지기 · 8 경비 반장 · 12 텃밭 보안관**.
- 「완벽한 문지기」: 색인의 모든 사건(12개)을 첫 실행에 해결. 이미 받은 배지는 그대로(배지는 뺏지 않음 — 기존 규칙).
- XP 사건마다 5, 합 60. 경제 시뮬레이션 중앙값이 v0.15.0(36.8 / 3.5일째)과 같아야 한다.

## 6. 확인 방법 (완료 기준)

- `tests/guard_incidents.py`: 12개 모두 ①~⑦(정답·빈칸 정답·오답 보기 모두 실패·전부 막기/들이기 실패·장별 허용 문법·시도 1~20개·장 순서) + **장마다 정확히 3개**, ko·en.
- 빌드 시험: `guard/chN-*.json` 4개가 생기고 서비스 작업자 목록에 있음, 배포 파일에 `solution` 없음, 첫 파일 < 844.6KB(v0.15.0 값, 숫자로 고정), 색인이 원본과 일치.
- 단위 시험: 색인·불러오기 모듈(받은 장 기억, 실패 시 거부), 등급 경계 0·4·8·12, 「완벽한 문지기」 12개 조건과 이미 받은 배지 유지, `cleanGuard`가 색인의 보기 수로 빈칸을 다듬음, 옛 저장(G1~G6만) 그대로.
- 화면 순회 시험: 장 파일을 받는 동안·실패했을 때 화면(다시 시도), 오프라인에서 경비실 열기, 새 사건 하나(G11) 빈칸으로 해결, 목록에 12개가 장 순서로.
- 브라우저 시험·경제 시뮬레이션·번역 시험·기존 묶음 회귀 없음.
- 아티팩트 체험판 다시 올리기(체험 저장은 1~6장 통과 그대로, `guard/` 파일 함께) — 구현 작업이 아니라 마지막에 대화를 진행하는 쪽이 한다(사용자 본인의 비공개 아티팩트, 이전 판과 같은 링크).
