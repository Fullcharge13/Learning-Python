# 「경비실」 응용 사건 15개 + 사건 파일 카드 설계 (v0.20.0)

- 작성일: 2026-11-14 · 상태: 사용자 검토 대기
- 브랜치: `feature/guard-room`에서 새 작업 브랜치(작업 시작 때 만듦)
- 바탕: `docs/specs/2026-11-12-경비실-설계.md`(엔진·저장), `docs/specs/2026-11-13-경비실-사건-12개-설계.md`(장 파일·문법 범위), `docs/specs/2026-11-13-경비실-v0.16.1-다듬기-설계.md`(어설픈 풀이 검사)
- 이 문서에서 **사용자가 고른 것**은 「(사용자)」, 나머지는 「(판단)」으로 적는다. 사용자는 판단 항목을 「제안 판단 따라가기」로 승인했다.

## 0. 이름 (사용자: A)

- 화면 이름은 **「응용 사건」**(꼬리표 「응용」), 영어 **"Field case"**(꼬리표 "Field"). 레슨의 「심화」(더 어려운 추가 레슨)와 헷갈리지 않게, 그리고 「어렵게가 아니라 넓게」라는 의도에 맞게.
- 코드·데이터 이름은 `tier: "field"`, 배지 `guard_files`.

## 1. 의도와 왜

- v0.16 설계 때 정한 방향: 장마다 기본 사건이 있고, 나중에 기본·심화로 나눈다. 이번이 그 「나중」이다. (화면 이름은 위 §0대로 「응용 사건」)
- **왜 (사용자)**: 어려운 단계를 만들려는 게 아니다. 기본에서 다루지 않은 공격 유형을 **응용 사건**으로 겪게 해서, 학습자가 나중에 사이버 보안을 배우거나 비슷한 공격을 실제로 만났을 때 **실마리**를 잡게 하려는 것이다.
- 그래서 응용의 핵심은 문법 난이도가 아니라 **새로운 공격 유형 + 현실과 이어 주는 카드**다.

## 2. 목표 · 하지 않을 것 · 실패로 볼 것

**목표**
- 3~17장마다 응용 사건 1개, 모두 15개(G46~G60) (사용자: A).
- 응용 사건은 그 장의 기본 사건 3개를 모두 해결하면 열린다 (판단).
- 응용 사건을 풀면 **「사건 파일」 카드**가 열린다: 실제 공격 이름(한·영), 현실에서 일어나는 모습, 내가 할 일, 더 찾아볼 검색어 (사용자: A).
- 15개를 모두 해결하면 배지 「사건 파일 수집가」 (판단).
- 한국어·영어 모두 완성.

**하지 않을 것 (이번 판)**
- 기본 45개에 사건 파일 카드 붙이기. 카드 데이터 모양은 같게 두어, 나중에 글만 쓰면 붙게 한다 (판단).
- 「보안 노트」 도감 화면 (사용자: C안은 나중). 카드는 사건 본문 안에 있으므로 나중에 모으면 된다.
- 장마다 응용 2개 이상 (사용자: A안 1개).
- 보상 수치 조정. 경제 밸런스는 다음 작업(3번)에서 따로 한다 (판단).
- 엔진(`src/py/guard.py`) 판정 방식 바꾸기. 응용 사건도 지금 세 방식(script·loop·func)과 block/allow 판정으로 만든다.
- 크로우 새 포즈.

**실패로 볼 것 (테스트가 통과해도)**
- 이미 받은 등급이 내려가거나, 「완벽한 문지기」 조건이 갑자기 멀어진다(응용가 기존 목표를 바꿈).
- 기존 해결 기록(G1~G45)이 사라지거나 XP를 다시 받는다.
- 카드 글이 실제 공격 **방법**(따라 할 수 있는 절차)을 가르친다. 카드는 개념·피해 모습·지키는 법까지만.
- 카드의 현실 정보가 틀렸거나 출처를 확인하지 않았다.
- 응용 사건이 기본 사건을 다른 말로 반복한 것이다(예: 6장 G11 「피싱 주소 확인」과 12장 스미싱이 같은 판정 규칙).
- 잠긴 응용 사건이 왜 잠겼는지 알 수 없다.

## 3. 제약 (기존 그대로)

- 공격은 가상 사건, 학습자 코드는 막는 쪽만. 인물·기관·주소는 가상(`.example` 도메인, 가상 기관명). 실존 서비스 이름을 공격 대상으로 쓰지 않는다. 비슷한 주소 사건도 가상 이름(예: `pinebank.example` ↔ `p1nebank.example`)으로.
- 사건은 **그 장까지 배운 문법만으로** 풀린다: `tests/guard_incidents.py`의 `NODES_BY_CH`·`IMPORTS_BY_CH`·`CALLS_BY_CH`·`METHODS_BY_CH`(누적) 그대로. 표를 넓히지 않는다.
- 판정은 시도마다 block/allow. 시도 값은 문자열이나 정수, 1~20개, block·allow 각 1개 이상. 언어별 값은 `value_en`.
- 코드 속 이름은 한·영 공통 영어. 영어 글은 `i18n/en/data.json`의 `guard.<id>.*` 열쇠.
- 사건 첫 해결에 XP 5(`GUARD_XP`), 바이트는 주지 않는다(판정 G-C2). 응용도 같다 (판단).
- 16장은 `sqlite3`를 쓰지 않고 SQL 글을 문자열로 검사, 17장은 그래프 없이 데이터 분석(v0.16 판정 그대로).
- 첫 파일 상한(`build.py`)과 장 파일 지문 이름 방식 그대로.
- 저장 형식(`saveVer` 2, `save.guard`) 바꾸지 않는다. 응용 해결도 `solved[id]`에 같은 모양으로 들어간다.

## 4. 만드는 방법 (사용자: A — 지금 사건 데이터에 표시만 더하기)

검토한 대안:
- **A (고름)**: 각 장 파일에 응용 사건을 하나 더 넣고 `tier: "field"`와 `file` 카드를 붙인다. 채점·재생·빈칸/직접 쓰기·오프라인·영어 팩을 그대로 쓴다.
- B: `guard/adv-chN.json`과 별도 화면. 기본·응용 구분은 뚜렷하지만 받기·미리 받기·화면을 새로 만들어 같은 일을 두 번 하는 코드가 생김.
- C: 카드만 `guard/files.json`에 모으기. 도감에 유리하지만 지금은 도감이 없어서 쓸 곳이 없고, 카드를 보려면 파일을 하나 더 받아야 함.

### 4-1. 데이터 (`data/guard.js`)

응용 사건은 기본 사건과 같은 칸에 아래 두 칸을 더한다.

```js
{
  id: "G46", need: 3, tier: "field", mode: "script", tag: "...",
  concept: "...", title: "...", brief: "...", ria: "...", crowIntro: "...", crowLose: "...", crow: {...},
  start: "...", blanks: [...], tries: [...], solution: "...",
  file: {
    attack: "MFA 피로 공격",       // 실제 공격 이름(한국어 화면용)
    alias: "MFA fatigue",          // 영어 원어(두 언어 모두에 보임)
    real: "...",                   // 현실에서 일어나는 모습 1~2문장
    todo: "...",                   // 내가 당하지 않으려면 할 일 1문장
    search: ["MFA 피로 공격", "MFA fatigue attack"],   // 더 찾아볼 검색어 1~3개
  },
}
```

- 놓는 자리: 각 장의 기본 3개 **바로 뒤**. 그래서 원본 순서는 「장 순서, 장 안에서는 기본 다음 응용」다.
- `tier`가 없으면 기본이다(기존 45개는 손대지 않음).
- `file`은 응용에만 필수. 기본에 있어도 화면은 같은 방식으로 보여 줄 수 있게 만든다(나중 대비, 이번에는 기본에 넣지 않음).
- 영어: `guard.<id>.file.attack`, `guard.<id>.file.real`, `guard.<id>.file.todo`, `guard.<id>.file.search.<n>`. `alias`는 이미 영어라 번역 열쇠가 없다(영어 화면에서 `attack`과 `alias`가 같으면 한 번만 보여 준다).

### 4-2. 색인과 장 파일 (`src/guard/catalog.js`)

- `guardIndexEntry`는 응용 사건에만 `tier: "field"`를 더한다(기본 칸 크기는 그대로).
- 장 파일 본문에는 `file`이 그대로 들어간다(카드는 장 파일과 함께 받아서, 오프라인에서도 보인다).
- `createGuardData`의 장 파일 검사는 그대로다(`need`가 맞는지).

### 4-3. 열림·등급·배지 (`src/guard/state.js`, `src/badges.js`, `data/badges.js`)

- `incidentOpen(entry, passed, guard, dev = false)`:
  - 기본: 지금처럼 `passed.has(need)`.
  - 응용: `passed.has(need)` 이고, (`dev`이거나 그 장의 기본 사건이 색인에서 모두 `guard.solved`에 있음).
  - 부르는 곳(목록, 첫 사건 고르기, `guardNews`)은 모두 저장의 guard와 개발자 표시(`isDev(save)`)를 넘긴다.
- 「새 소식 점」(`guardNews`)은 열린 사건만 센다. 그래서 기본 3개를 다 푼 순간 응용가 열리며 점이 뜬다.
- **등급과 「완벽한 문지기」는 기본 사건만 센다** (판단). `rankThresholds(기본 수)`, `rankOf`는 기본 해결 수, `guard_perfect`는 기본 전부 첫 실행 해결. 이유: 응용를 등급에 넣으면 기존 학습자의 등급 기준이 45→60으로 올라 「보안관」이 갑자기 멀어진다(실패로 볼 것 첫 줄). 이미 받은 배지는 지금처럼 그대로 남는다.
- 화면 머리의 「n/45 해결」은 기본 기준 그대로 두고, 응용는 따로 「사건 파일 m/15」로 보인다.
- 새 배지 `guard_files` 「사건 파일 수집가」: 응용 사건을 모두 해결. 배지 그림 칸은 `src/ui/badges.js`의 기존 방식(색·글자)으로 `m/15`.
- `guard_perfect`의 설명이 아직 「사건 6개」로 되어 있어(v0.15 글) 「기본 사건을 모두 첫 실행에 해결해요」로 고친다(영어도).

### 4-4. 화면 (`src/ui/guard.js`)

- **사건 목록**: 장 안에서 응용 사건은 기본 다음 줄에, 「응용」 꼬리표와 파일 그림(기존 아이콘 묶음 안에서)을 단다.
  - 장을 아직 안 끝냈으면 지금처럼 「N장을 끝내면 열려요」.
  - 장은 끝냈는데 기본이 남았으면 「기본 사건 3개를 풀면 열려요」와 남은 수(예: 「1개 남음」).
- **사건 카드**: 응용 사건은 제목 옆에 「응용」 꼬리표.
- **처음 해결 창**(`solvedDialog`): 응용면 기존 내용 아래에 사건 파일 카드를 붙인다. 카드 모양:
  - 머리: 파일 그림 + 「사건 파일」 + 공격 이름(그리고 원어)
  - 「현실에서는」 `real`
  - 「나를 지키려면」 `todo`
  - 「더 찾아볼 말」 `search`를 작은 꼬리표로(누르면 복사 정도만, 링크·검색창 열기는 하지 않음 (판단): 앱 밖으로 내보내는 길을 만들지 않고, 오프라인에서도 똑같이 보이게)
- **다시 보기**: 해결한 응용 사건을 다시 열면 사건 카드 안에 「사건 파일 보기」 단추. 누르면 같은 카드를 창으로.
- 어두운 화면·영어·좁은 화면에서도 대비 4.5:1(`tests/contrast.py`에 이 카드 화면을 더함).
- 카드 글은 데이터에서 오므로 화면에 넣을 때 모두 `esc`(v0.19.2 출력 점검 원칙).

### 4-5. 개발자 모드

- 개발자 모드 저장에서는 응용 사건도 모두 열린다(장 통과·기본 해결 조건을 건너뜀). 해결 기록은 지금처럼 개발자 칸에만 남는다.

- 표의 「방어 판단」은 방향이다. 정확한 시도 목록·빈칸·방식(script/loop/func)·`why` 글은 만드는 사람이 정하되, 아래 §6 검사를 모두 통과해야 한다.
- 겹침 주의(실패로 볼 것): G55는 G11(피싱 주소: 주소 구조)·G29(피싱 메시지 탐지)와 **판정 규칙이 달라야** 한다. G55는 「짧은 주소 + 미끼 말이 함께」. G56은 G31(도메인 구조)과 달리 「QR 속 주소」라는 상황과 `urlparse` 사용. G57은 G12(위험한 입력 거르기)와 달리 「JSON 게시글 + 보여 주기 전」. 만드는 사람은 각 사건의 `concept`에 기본 사건과 다른 점을 한 줄로 적는다.
- 카드 `real`·`todo`는 공식 자료(KISA·경찰청·국가정보원·과학기술정보통신부·OWASP 등)로 사실을 확인하고, 출처를 `docs/security/2026-11-14-사건-파일-출처.md`에 사건마다 적는다(앱에는 출처를 넣지 않음). 프로젝트 문서 「2026 국가정보보호백서」·「소프트웨어 개발보안 가이드」를 우선 참고한다.

## 6. 확인하는 법 (성공의 증거)

- `tests/guard_incidents.py`
  - 기존 ①~⑩을 응용 15개에도 그대로(정답 해결, 오답 보기 실패, 전부 막기·전부 들이기 실패, 장 문법 범위, 시도 수, 어설픈 풀이 실패).
  - ⑦⑧ 바꿈: `WANT_IDS`·`WANT_CHAPTERS`에 장마다 기본 3 + 응용 1(응용는 장의 마지막). 「장마다 기본 정확히 3개, 응용 정확히 1개」.
  - 새 검사: 응용에는 `file`이 있고 `attack`·`alias`·`real`·`todo`가 비어 있지 않고 `search`가 1~3개. 기본에는 `tier`가 없음.
  - 응용마다 `WRONG_SOLUTIONS`에 어설픈 풀이 1개 이상.
- 단위 시험(`npm test`)
  - `incidentOpen`: 장 미통과 → 닫힘, 장 통과·기본 2/3 → 닫힘, 3/3 → 열림, 개발자 → 열림. 기본은 예전 그대로.
  - `rankOf`·`rankThresholds`가 기본 수(45)만 셈. 응용를 풀어도 등급 기준이 바뀌지 않음.
  - `guard_perfect`는 기본만, `guard_files`는 응용 15개 해결로.
  - `guardNews`: 기본 3개를 푼 직후 응용 하나 때문에 점이 뜸.
  - `guardIndexEntry`: 응용만 `tier`가 붙음.
  - 사건 파일 카드 HTML이 데이터 글을 `esc`함(`tests/unit/output_escape.test.js` 방식).
- 화면 흐름(`tests/flow.py`)
  - 응용는 잠겨 있고 이유(남은 수)가 보임 → 기본 3개 해결 → 열림 → 해결 → 처음 해결 창에 사건 파일 카드 → 다시 열면 「사건 파일 보기」.

## 7. 만드는 사람에게 맡기는 것

- 각 사건의 시도 목록·빈칸 보기·방식·`why`·리아·크로우 대사, 카드 문장. (§5 방향과 §6 검사 안에서)
- 「응용」 꼬리표와 카드의 정확한 색·여백(기존 토큰 안에서, 밝게·어둡게 대비 통과).
- 카드 「더 찾아볼 말」 누르기 동작은 복사 또는 아무 동작 없음 중 간단한 쪽.

## 8. 검토에서 정한 것 (판단, 설계 검토 질문에 대한 답)

- **G54 해시**: 학습자 코드가 해시를 계산하지 않는다(11장에 `hashlib`이 없고 문법 표를 넓히지 않음). 엔진의 `files`로 「기록된 지문」 파일을 주고, 시도마다 온 「파일 이름, 지문」을 기록과 **문자열로 비교**한다. `concept`과 카드 `real`에 「실제로는 프로그램이 파일 내용으로 지문을 계산한다」를 한 줄 적는다.
- **카드 사실 확인**: 카드 글은 진행자(이 세션)가 웹 검색과 프로젝트 문서로 확인해 `docs/security/2026-11-14-사건-파일-출처.md`에 문장과 출처를 먼저 적고, 사건을 만드는 사람은 그 문장을 쓴다. 확인 못 한 구체적 사실(기관별 역할, 금액·건수 같은 수치)은 **넣지 않고 일반적인 말로** 쓴다. 카드에 수치는 넣지 않는다.
- **열림 판정 재료**: 기본 사건은 「같은 `need`, `tier`가 `"field"`가 아님」. 색인은 첫 파일에 있으니 열림 판정은 장 파일 없이 색인과 저장만으로 한다(받기 실패와 무관). `incidentOpen` 인자를 늘리고 부르는 곳(`src/ui/guard.js`, `guardNews`, 그 밖의 호출)을 모두 고친다.
- **기본만 세는 것**: 사용자에게 「45」로 보이거나 45에서 나오는 것은 모두 기본만 센다 — 등급, 머리 「n/45 해결」, `guard_perfect`와 그 그림 `n/n`. 응용는 따로 「사건 파일 m/15」. `guard_first`(아무 사건이나 첫 해결)는 그대로. 퀘스트·이정표는 XP 경로라 그대로(아래).
- **XP**: 응용 첫 해결도 XP 5가 같은 길(earnXp·퀘스트 「xp」·연속)로 흐른다. 15개 합쳐 75 XP. 사용자가 「XP 5, 수치 늘리지 않음」을 승인했다.
- **개발자 모드**: 기본 사건과 같은 규칙(개발자 칸 저장에서 배지도 같은 규칙으로 받음, 학습 기록과 섞이지 않음).
- **겹침 기계 검사**: `tests/guard_incidents.py`에 검사 추가 — G55·G56·G57의 정답 풀이를 G11·G29·G12·G31의 시도 목록으로 돌리면 해결에 **실패**해야 한다(같은 판정 규칙이 아님을 확인). 방식이 달라 돌릴 수 없는 짝은 문서로만 적는다.
